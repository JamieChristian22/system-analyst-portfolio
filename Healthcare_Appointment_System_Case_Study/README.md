## 📌 Case Study Overview

The **Healthcare Appointment Management System** is a realistic end-to-end Systems Analyst portfolio simulation focused on modernizing outpatient appointment scheduling through self-service booking, centralized availability, automated reminders, secure payment authorization, role-based access, system integrations, auditability, operational reporting, and structured production support.

The case study demonstrates how a Systems Analyst translates a business problem into a complete system-delivery model:

**Business Need → Requirements → Process Analysis → System Design → APIs & Integrations → Data → Security → Testing → Implementation → Production Support**

The project was designed to demonstrate the responsibilities expected from a Systems Analyst working between:

- Business stakeholders
- Patient access teams
- Scheduling operations
- Application teams
- Integration teams
- Data teams
- Security and privacy
- Quality assurance
- Infrastructure
- Production support
- External technology vendors

# 🎯 Business Problem

The simulated outpatient healthcare organization relied heavily on telephone-based appointment scheduling.

Scheduling staff manually:

- Verified patients
- Searched multiple provider calendars
- Identified available appointment slots
- Entered appointments
- Managed cancellations
- Rescheduled visits
- Maintained waitlists
- Sent reminders
- Coordinated provider changes
- Tracked scheduling issues
- Reconciled operational reports

This process created several business and system problems.

| Problem | Impact |
|---|---|
| Phone-first scheduling | Long patient wait times |
| Manual availability searches | High administrative effort |
| Disconnected provider calendars | Booking errors |
| Manual reminders | Increased no-shows |
| Manual waitlists | Lost earlier-booking opportunities |
| Fragmented payment process | Additional staff effort |
| Limited self-service | High call-center demand |
| Weak auditability | Reduced compliance visibility |
| Spreadsheet reporting | Delayed operational insight |
| Inconsistent exception handling | Increased support workload |

The organization required an integrated appointment-management solution that could improve both **patient experience and operational efficiency**.

# 📖 Business Rules

Key business rules include:

- Provider slots are unique by provider, location, start time, and service.
- Appointment duration is defined by service type.
- New-patient appointments require identity verification.
- Same-day cancellations require a reason.
- Waitlist ranking considers urgency, requested date, and enrollment timestamp.
- Reminder channel follows communication preference.
- Full payment card numbers are never stored.
- Staff overrides require authorized role and reason.
- Cancelled slots become searchable after transaction completion.
- Audit events cannot be modified by standard application users.

# ⛔ Go / No-Go Criteria

The implementation does not proceed if:

- Severity 1 defect remains open.
- Critical integration is unavailable.
- Data reconciliation fails.
- Production authentication fails materially.
- Monitoring is unavailable.
- Rollback is not executable.
- Material security controls fail.

---

# ↩️ Rollback Plan

Rollback is considered when:

- Appointment creation becomes unreliable.
- Data integrity is at risk.
- Access controls fail materially.
- Critical dependencies cause widespread failure.
- A Severity 1 defect cannot be contained.

### Rollback Steps

1. Disable patient web booking.
2. Place system into maintenance mode.
3. Stop background consumers.
4. Restore previous application version.
5. Reverse compatible database changes or restore approved backup.
6. Re-enable previous staff workflow.
7. Validate control totals.
8. Communicate status.
9. Create incident record.
10. Preserve diagnostic evidence.

# 🚨 Incident Triage & RCA

## Example Incident

**Incident ID:** INC-2026-017  
**Severity:** P2

### Symptom

A subset of confirmed appointments failed to receive SMS confirmation during a simulated 43-minute external messaging-provider disruption.

### Impact

- 64 appointments affected
- Appointment bookings remained successful
- No appointment data was lost
- Email confirmation continued where configured

### Root Cause

The external SMS provider experienced elevated timeout rates.

The application's retry behavior retried too aggressively against the degraded dependency.

### Corrective Actions

1. Implement exponential backoff.
2. Add retry jitter.
3. Add circuit-breaker logic.
4. Add provider-health monitoring.
5. Update the operational runbook.
6. Add sustained-timeout regression testing.
7. Monitor performance by communication channel.

# 🧠 Key Lessons Demonstrated

## Requirements Need End-to-End Traceability

A business requirement has more value when it can be traced through:

**Functional Requirement → System Component → Interface → Test Case → Result**

---

## Systems Analysts Must Understand Failure Scenarios

Integration analysis should document both:

- Successful interaction
- Dependency failure behavior

Retries, timeouts, errors, rollback, and support paths are part of system analysis.

---

## Business and Technical Requirements Are Connected

Patient wait times and booking errors are business problems, but improvements depend on technical capabilities such as:

- Search performance
- Transaction integrity
- API reliability
- Availability
- Monitoring
- Integration stability

---

## Nonfunctional Requirements Matter

Functionality alone does not make a system production-ready.

The system must also meet:

- Performance
- Availability
- Scalability
- Security
- Recovery
- Accessibility
- Observability

requirements.

---

## Security Must Be Designed Into the System

Authentication, authorization, encryption, logging, privacy, and role permissions should be defined during analysis rather than added after implementation.

---

## Testing Starts With Requirements

Clear acceptance criteria and traceability make UAT more objective and reduce ambiguity between business and technical teams.

---

## Implementation Is Part of Systems Analysis

Production readiness, cutover, rollback, monitoring, and support are essential elements of a complete system lifecycle.

---

## Incidents Create Improvement Opportunities

Root-cause analysis should feed changes back into:

- Requirements
- Architecture
- Monitoring
- Testing
- Error handling
- Support documentation
